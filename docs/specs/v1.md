# Project Brief — Souls-Inspired Fitness App

*Handoff doc for a coding assistant. This is a separate project from "Snaply" — do not conflate the two.*

## 1. Concept summary

A mobile fitness app that bridges real-world walking with dark-fantasy, Souls-borne-style game mechanics. Step counts and walking distance unlock in-game items and boss encounters. The design goal is a polished, legally defensible, atmospheric experience built on **original mythology** — not a reskin of any existing IP.

---

## 2. Core mechanics (confirmed)

- **Distance milestones unlock armaments.** E.g. 3km walked → an armament; 5km → a more powerful armament. (Exact curve/tiering still open — see Section 8.)
- **Boss encounters** require walking 5km/day for 5 consecutive days.
- **Death mechanic:** missing a day of a boss streak causes "death" — but this **only resets that specific boss encounter's progress**, not the player's overall build, level, or owned armaments. The player returns to their last checkpoint.
- **Checkpoints** act as safe, banked-progress markers (functionally a "bonfire," but must use original terminology — see Section 5).
- **Illness/affliction system:** self-reported via an in-character questionnaire (e.g. "has an affliction struck you?"). Relies on player honesty; this matters for leaderboard integrity. When active, the affliction should function as a **status debuff that pauses the boss-fight timer without breaking the streak** — a diegetic mechanic, not a settings toggle. **This system is deliberately deferred for post-v1 iteration** — for v1, keep it minimal/stubbed.

## 3. V1 scope

**In scope:**
- Checkpoints
- Competitive leaderboards
- Nearby partner-finding (a "summons" equivalent — find/connect with friends or nearby players)
- Anonymous death markers (a "bloodstain" equivalent) — shows where another player's boss attempt ended, as a fixed icon/type (e.g. "died here, attempt #3"), **not free text**

**Explicitly cut from v1:**
- User-generated custom messages on death markers — cut due to moderation overhead. If added later, needs a moderation pipeline first.

**Deferred to post-v1:**
- Full illness/debuff iteration (see Section 2)

## 4. Legal / IP constraints — read before writing any user-facing strings

This is a structural requirement, not a style preference.

- **Game mechanics are not protected IP.** Checkpoints, death-and-return loops, stamina-style systems, environmental-storytelling item descriptions, invasion/summon-style multiplayer — all standard "soulslike" genre conventions, safe to use freely.
- **Specific proper nouns and named terminology from existing games are the actual risk.** Do not use, even as placeholders in code or comments: *Tarnished, Scarlet Rot, Site of Grace, Bloodstain* (as a literal term), or any other FromSoftware-specific vocabulary. A cease-and-desist doesn't require a lawsuit to hurt this project — app stores can pull a listing on receipt of a C&D alone.
- **The fix is architectural:** all user-facing fictional terminology must be resolved through a **world-agnostic terminology lookup table** (see Section 6), never hardcoded into engine/UI code. This makes it structurally impossible for a trademarked term to leak into a shipped string.
- Cross-cultural sleep-paralysis folklore (Old Hag syndrome, kanashibari, Pisadeira, incubus/succubus lore) is public-domain and safe to draw thematic inspiration from.

## 5. World-agnostic engine architecture

**Core principle:** the mechanics engine (steps, armament tiers, boss timers, checkpoints, affliction states) must be completely world-agnostic — it only ever deals in generic keys and numbers, never fictional names. A "world" is a pure content bundle layered on top. Build this abstraction from day one, even though v1 ships with exactly one world — retrofitting it later after mechanics and lore strings get tangled is expensive; building it now is nearly free.

### Data models

**`World`**
```json
{
  "world_id": "w_endless_paralysis",
  "name": "The Endless Paralysis",
  "tone": "eerie, oneiric, restrained — not jump-scare horror",
  "pillars": ["the_watcher", "the_weight", "the_hollow_hour", "the_second_face", "the_long_blink"],
  "art_theme": "endless_paralysis_palette",
  "active": true
}
```

**`Terminology`** (per world — every fictional string the engine would otherwise hardcode)
```json
{
  "world_id": "w_endless_paralysis",
  "terms": {
    "PLAYER_TITLE": "the Half-Woken",
    "CHECKPOINT_NAME": "a Held Breath",
    "DEATH_MARKER_NAME": "a Failed Waking",
    "AFFLICTION_NAME": "the Weight",
    "ARMAMENT_CATEGORY_WEAPON": "Wakings",
    "ARMAMENT_CATEGORY_ARMOR": "Linens",
    "BOSS_ENCOUNTER_LABEL": "the Long Night"
  }
}
```
All notification strings, UI labels, and boss-fight screens must be built from `{TEMPLATE_KEYS}` resolved against this table at render time — never a literal string in engine code.

**`LoreFragment`**
```json
{
  "fragment_id": "f_00231",
  "world_id": "w_endless_paralysis",
  "trigger_type": "milestone_km",
  "trigger_value": 5,
  "pillar_tags": ["the_weight"],
  "rarity_weight": 1,
  "text": "The Weight doesn't crush you. It just reminds you what your legs are for, in case you forgot."
}
```
`trigger_type` enum: `daily_ambient`, `milestone_km`, `armament_unlock`, `boss_kill`, `boss_death`, `affliction_status`, `checkpoint_return`.

**`PlayerWorldProgress`** (kept separate from core player stats, so swapping worlds never touches real progress)
```json
{
  "player_id": "p_9931",
  "world_id": "w_endless_paralysis",
  "seen_fragment_ids": ["f_00201", "f_00214"],
  "world_started_at": "2026-07-01"
}
```

### Lore delivery — two-tier system

- **Ambient tier:** one small guaranteed fragment per day, just for opening the app, independent of activity. Keeps the world alive on zero-step days; the daily re-engagement hook.
- **Earned tier:** richer fragments gated behind distance milestones, armament unlocks, and boss kills — piggybacks on rewards the app already grants.

### Content pipeline
- Author lore as flat YAML/JSON per world, one file per trigger type.
- A lint script should check: every terminology key filled, minimum fragment pool size per trigger type (avoid near-term repeats), no cross-world pillar tag leakage.
- No CMS needed for v1; flat files in-repo are sufficient.

### Runtime behavior
- **Lore delivery service:** given `(world_id, trigger_type, trigger_value, seen_fragment_ids)` → weighted-random unseen fragment, falling back to least-recently-seen once exhausted.
- **World switch** = changing `player.active_world_id`. Core stats/streak/armament state never move — only the skin and lore-progress pointer change.

## 6. Mythos (v1 world)

**World:** *The Endless Paralysis* — the world didn't end in fire or flood; it ended in a night that never fully lifted. Everyone is technically awake and technically asleep at once. Motion is what convinces the body it's real.

**Tone requirement:** eerie, atmospheric, restrained dread — explicitly **not** jump-scare horror. This theme sits close to a real, common human experience (sleep paralysis) that a meaningful share of players may have personally lived through; the design goal is "moody and cool," not something that could trigger a genuine panic response in a daily-use app.

**Pillars / boss archetypes:**
| Pillar | Phenomenon |
|---|---|
| The Watcher | the felt presence at the foot of the bed |
| The Weight | chest pressure, can't move, can't scream |
| The Hollow Hour | the 3am dread-spike |
| The Second Face | a hypnagogic hallucination that looks like someone familiar, but isn't |
| The Long Blink | time distortion — seconds and hours become indistinguishable |

**Authoring pattern for new fragments:** name an ordinary object or ritual (a boot, a bell, a doorway, an invitation) and let the *wrongness of its stillness* imply the catastrophe — never narrate the backstory directly. Consistency of a small set of recurring objects/pillars across unrelated fragments is what makes the mythos feel coherent; the player assembles the connective tissue themselves.

Sample fragments (all 7 trigger types) exist from prior design work and should be expanded to a full authoring pool (aim for enough per trigger type that a daily user doesn't see repeats for at least ~2 weeks).

## 7. Visual direction

**Target:** stylized, eerie, deliberately non-photorealistic — "wrong-feeling," not hyperreal. This is a deliberate choice, not a budget constraint: hyperrealism was judged to work against the intended atmosphere.

Confirmed techniques:
- Restricted color palette with a single intrusive accent color
- Cel/toon shading or banded (non-smooth) lighting rather than PBR realism
- Painterly / hand-baked textures instead of physically-based materials
- Silhouette-first design for bosses/afflictions — readable as shape before detail resolves
- Heavy fog/darkness as both an atmosphere tool and a practical way to avoid rendering full detail at distance
- Post-processing as a primary "eerie" lever: chromatic aberration (pulsed during affliction states), film grain, vignette tightening during boss encounters, screen-warp/double-vision during "the Long Blink"
- Deliberately "wrong" animation timing (held frames, non-human blend curves) for uncanny character moments — cheaper than any texture/rendering work and highly effective

Typography/UI: use an original serif typeface (e.g. EB Garamond, Cormorant, Cinzel — not FromSoftware's actual font) and an original accent color, per the IP constraints in Section 4.

## 8. Tech stack (confirmed direction)

**No traditional game engine (Unity/Godot).** Reasoning: this app's actual interaction model is timers, counters, and unlock-triggered reveal screens — not real-time player-controlled simulation, physics, or combat. Game engines earn their complexity budget when you need real-time simulation; this app doesn't, so skipping one is the more correct architecture, not a compromise.

**Chosen stack: Flutter, using the Impeller renderer.**
- Impeller is Flutter's current default, production-stable renderer on both iOS and modern Android; it pre-compiles shaders at build time, avoiding first-run stutter — important for reliability on the dramatic "reveal" moments (armament unlock, boss kill/death screens).
- Flutter has an edge over React Native specifically for animation-heavy, custom-graphics apps, which this is once you set aside the "game" label.
- Flutter supports custom GLSL-based fragment shaders directly — this is the implementation path for the post-processing effects in Section 7 (chromatic aberration, vignette, grain, banded/cel lighting).

**Rive** for character/boss/affliction animation:
- Hand-authored 2D vector illustrations with state machines (idle → triggered → death → return), exported from Rive's editor and played in Flutter.
- This is a better fit for the stylized/non-realistic goal than real-time 3D models — every frame is hand-art-directed, which is how the "deliberately wrong" quality (Section 7) actually gets achieved, rather than fought against generic 3D asset defaults.

**Explicitly not in v1, revisit later if needed:**
- An explorable 3D world map (camera moving through real 3D space) is the one thing this stack doesn't give cheaply. If it becomes a real requirement post-launch, the two paths are: (a) Unity-as-a-Library embedded just for that one screen, or (b) a WebGL layer (e.g. Three.js) in a webview for a lighter pseudo-3D map. Do not build for this up front — validate that players actually want an explorable map before adding this complexity.

**Backend (not yet deeply specced):** Firebase or Supabase are the standard low-overhead choices for a solo developer, covering leaderboards, world/lore-pack delivery, and nearby-player/summon matching.

**Health data integration:** HealthKit (iOS) and Health Connect (Android) for step/distance tracking. Both have mature Flutter plugin support.
